# Case Filing AI Second Handoff

## Summary

We narrowed the plan from a large modular architecture into a small first prototype.

The prototype should prove this loop:

```text
Upload part rule + multiple PDFs
→ backend saves files
→ backend processes one document at a time
→ embedded text extracted first
→ one master prompt extracts structured data
→ local JSON saves output
→ case snapshot updates after each document
→ frontend shows status and results
```

## Main decisions

| Topic | Decision |
|---|---|
| Module name | Use `case-filing-ai`, not `docketing-ai` |
| First storage | Local JSON, not database |
| Processing | Upload many files, process one document at a time |
| Context | Prior case snapshot guides later docs, but does not confirm facts |
| Rules | Paste/upload part rule text for prototype |
| OCR | Mark `ocr_needed` if embedded text is bad; full VL OCR can come later |
| Human review | Only OCR/handwriting/visual uncertainty blocks workflow |
| Backend queue | Backend owns processing and logs |
| Frontend | Upload, show status, show results |

# Cursor Prompt

Build a small Case Filing AI prototype.

Do not build database.  
Do not add authentication.  
Do not add unrelated features.

## Goal

Create a frontend and backend workflow where I can:

1. Paste or upload part rule text.
2. Upload multiple synthetic NYSCEF-style PDF filings.
3. Click Process.
4. Backend saves the files.
5. Backend processes the PDFs one document at a time.
6. Backend extracts embedded PDF text first.
7. If embedded text is missing, garbled, incomplete, scanned, or unreliable, mark `ocr_needed: true`.
8. Backend sends current document text + prior case snapshot + part rule text to one master prompt.
9. Backend saves each document result as JSON.
10. Backend updates `case-snapshot.json` after each document.
11. Frontend shows processing status and final extracted results.

## Backend

Create:

```text
backend/src/modules/case-filing-ai/
  routes/
    caseFiling.routes.ts

  controllers/
    caseFiling.controller.ts

  services/
    uploadBatch.service.ts
    pdfText.service.ts
    masterPrompt.service.ts
    caseSnapshot.service.ts
    localJsonStore.service.ts

  prompts/
    master-case-filing.prompt.md
```

Backend behavior:

1. Save uploaded PDFs locally.
2. Save pasted/uploaded part rule text locally.
3. Sort files by:
   1. NYSCEF document number if available
   2. filed date/time if available
   3. filename
   4. upload order
4. Process PDFs one at a time.
5. Extract embedded PDF text first.
6. If embedded text is bad, mark `ocr_needed: true`.
7. Send this to the master prompt:
   - current document text
   - current file metadata
   - prior case snapshot
   - part rule text
8. Save each document output as JSON.
9. Update `case-snapshot.json` after each document.
10. Write `processing-log.jsonl`.

## Master Prompt Rules

Create `master-case-filing.prompt.md` with this behavior:

```text
You are processing one synthetic NYSCEF-style filing at a time.

Inputs:
- Current document text
- Current file metadata
- Prior CaseStateSnapshot
- Relevant part rule text

Rules:
- Prior case context can guide interpretation.
- Only the current document can confirm new facts.
- Do not overwrite confirmed facts silently.
- Save AI output as unreviewed.
- Only require human review for OCR, handwriting, checkbox, stamp, postal receipt, signature/date, or visual uncertainty.
- If embedded text appears incomplete or garbled, mark ocr_needed.
- Later documents may enrich, correct, or supersede earlier provisional data.
- Apply only the supplied part rule text.
- Do not invent court practices.
- Do not calculate deadlines unless the document, part rule, or prior confirmed context supports it.
- If unsure, mark status as provisional or needs_review instead of guessing.

Return strict JSON:
{
  "documentMetadata": {},
  "extractionQuality": {},
  "docketEntry": {},
  "caseUpdates": {},
  "parties": [],
  "witnesses": [],
  "tasks": [],
  "deadlines": [],
  "humanReviewItems": [],
  "updatedCaseSnapshot": {},
  "auditNotes": []
}
```
